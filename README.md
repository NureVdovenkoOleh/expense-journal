# Журнал особистих витрат

Наскрізний проєкт з дисципліни «Програмування мовою Dart», **варіант 3**.

Основна сутність — **витрата** з полями: ідентифікатор, дата, категорія,
сума, валюта, спосіб оплати, примітка.

Поточна версія — **1.0.0, лабораторна робота 4** (мітка `lab4`):
консольний застосунок, який веде журнал у файлі JSON, обробляє текстові
файли будь-якого розміру й отримує офіційні курси НБУ, а також
HTTP-служба на `shelf` з доступом до тих самих даних. Історію версій
описано в [CHANGELOG.md](CHANGELOG.md); попередні стани доступні за
мітками `lab1`–`lab3`.

## Встановлення

Потрібен Dart SDK 3.13 або новіший (використано первинні конструктори).

```
git clone https://github.com/NureVdovenkoOleh/expense-journal.git
cd expense-journal
dart pub get
dart test
```

## Консольний застосунок

```
dart run expense_journal <команда> [аргументи]
```

| Команда | Що робить |
|---|---|
| `import [файл]` | додає витрати з текстового файлу (без файлу — вбудовані приклади) |
| `list [--category К] [--currency UAH\|USD\|EUR]` | друкує витрати з журналу |
| `report` | друкує текстовий звіт |
| `generate [-n кількість] [-o файл]` | створює великий файл для перевірки `stats` |
| `stats <файл>` | рахує суми за категоріями, читаючи файл рядок за рядком |
| `rates [--endpoint url]` | порівнює умовні курси з офіційними курсами НБУ |

Глобальна опція `-d, --data` задає файл журналу (за замовчуванням
`data/expenses.json`). Довідка — `--help` або `help <команда>`.

Формат рядка текстового файлу:
`id;дата;категорія;сума;валюта;спосіб оплати;примітка`, наприклад
`E01;2026-09-03;Продукти;845.50;UAH;картка:5375414100009876;Сільпо`.

Повідомлення про помилки йдуть у `stderr`, а код завершення пояснює
причину (значення з BSD `sysexits.h`):

| Код | Значення |
|---|---|
| 0 | успіх |
| 64 | неправильні аргументи командного рядка |
| 65 | некоректні дані (файл журналу, порожній журнал) |
| 69 | служба курсів недоступна або відповіла кодом не 2xx |
| 74 | помилка читання чи запису файлу |
| 76 | служба курсів повернула некоректне тіло |

Швидший запуск — скомпільований файл:

```
dart compile exe bin/expense_journal.dart -o build/expense_journal.exe
build/expense_journal.exe list
```

## HTTP-служба

```
dart run expense_journal import      # наповнити журнал
dart run expense_journal:server      # http://127.0.0.1:8080, зупинка — Ctrl+C
```

Порт можна змінити змінною середовища `PORT`. Служба читає той самий
`data/expenses.json` і зберігає в нього кожну нову витрату.

| Запит | Відповіді |
|---|---|
| `GET /items?category=…&currency=…&minAmount=…` | 200 — масив витрат; 400 — некоректний фільтр |
| `GET /items/<id>` | 200 — витрата; 404 — немає |
| `POST /items` (тіло — JSON витрати) | 201 + `location`; 400 — некоректне тіло чи значення; 409 — такий `id` вже є |
| будь-який інший | 404 |

Усі відповіді — `application/json; charset=utf-8`; помилки мають вигляд
`{"error": "пояснення"}`. Номери карток і рахунків у відповідях
замасковано.

Приклад (PowerShell; кирилицю в адресі слід кодувати, інакше PowerShell
передасть її в кодуванні консолі):

```
curl.exe -i http://localhost:8080/items/E05
curl.exe -i "http://localhost:8080/items?category=%D0%9A%D0%B0%D1%84%D0%B5"
curl.exe -i -X POST http://localhost:8080/items -H "content-type: application/json" --data-binary "@data\new.json"
```

### Розподіл коду між `bin/` і `lib/`

У `bin/` лишилися лише точки входу: `bin/expense_journal.dart` — один
рядок `exitCode = await runCli(arguments);`, `bin/server.dart` — запуск
сервера. Уся логіка винесена в `lib/`, бо код у `lib/` можна імпортувати
в тести, а код з `bin/` — ні. Завдяки цьому команди й маршрути служби
перевіряються тестами без запуску окремого процесу чи відкриття порту.

Реалізація лежить у `lib/src/`, а `lib/expense_journal.dart` лише
реекспортує її. За домовленістю Dart файли з `src/` напряму не
імпортують, тож внутрішню структуру можна змінювати, не ламаючи коду,
що використовує пакет.

### Чому `lib/` поділено на кілька файлів

Кожен файл містить одне поняття предметної області або один етап
обробки. Залежності йдуть в один бік: модель (`currency`,
`payment_method`, `expense`) нічого не знає про розбір, аналітику й звіт.
Фасад реекспортує все, тож у `bin/` і тестах один `import`.

Запечатаний клас `PaymentMethod` і всі його підтипи оголошено в одному
файлі: цього вимагає `sealed` — підтипи поза бібліотекою заборонені.

## Модель предметної області

| Що | Тип | Чому |
|---|---|---|
| Витрата | незмінний клас `Expense` | Усі поля `final`, конструктор константний. Об'єкт, який не змінюється, безпечно класти в `Set`, використовувати як ключ `Map` і кешувати. |
| Валюта | `enum Currency` з полями `symbol`, `rateToUah` і методом `toUah` | У ЛР 1 валюта була рядком, і невідомий код виявляв валідатор. Тепер невідомої валюти не може існувати: помилка виявляється під час розбору. Курс у переліченні дозволяє додавати суми різних валют. |
| Спосіб оплати | `sealed class PaymentMethod` з підтипами `Cash`, `CardPayment`, `BankTransfer` | Способи оплати мають різні дані (картка — номер, переказ — IBAN, готівка — нічого) і різну поведінку (комісія). Рядок або перелічення цього не виражають. |
| Результат розбору | запис `({Expense? expense, String? error})` | Залишено з ЛР 1: запис пояснює, чому рядок відкинуто. |
| Статистика сум | запис `({double min, double max, double average})` | Функція повертає три значення одразу; окремий клас для цього надлишковий. |
| Сховище | `Repository<T extends Identifiable>` | Одна реалізація для будь-яких сутностей з ідентифікатором. |
| Сума | `double` | Як у ЛР 1; відомий недолік — похибка двійкових дробів, суми виводяться з двома знаками після коми. |

## Ключові проєктні рішення

### Конструктори класу `Expense`

- **Первинний константний конструктор** `class const Expense({...})`
  оголошує поля й параметри в заголовку класу.
- **`Expense.fromCsv(line)`** замінює функцію розбору з ЛР 1. Конструктор
  не може повернути `null`, тому для пошкодженого рядка він кидає
  `FormatException` — так само, як `int.parse`.
- **`Expense.cached(line)`** — фабричний конструктор з кешем: для рядка,
  який уже розбирали, повертає наявний екземпляр. Генеративний
  конструктор так не вміє, бо завжди створює новий об'єкт.

Другий приклад фабричного конструктора — `PaymentMethod.parse(text)`:
він обирає, екземпляр якого підтипу створити, а для готівки повертає
той самий константний `Cash()`.

### Перехід на первинний конструктор (Dart 3.13)

Спершу клас було написано класично: сім оголошень полів і окремий
конструктор із `this.id, this.date, ...` (близько 25 рядків). Після
переходу поля й конструктор оголошуються один раз, у заголовку класу
(9 рядків).

Що **змінилося**:

- клас із первинним конструктором не може мати інших генеративних
  конструкторів, які не перенаправляють виклик, тому `Expense.fromCsv`
  став фабричним, а допоміжний приватний конструктор зник;
- ключове слово `const` перемістилося: `class const Expense(...)`;
- правило `public_member_api_docs` вимагає окремого коментаря для
  конструктора — коментар класу його не документує. Тому в тілі класу
  додано оголошення `this;` з документаційним коментарем;
- загальний обсяг файлу майже не змінився (112 → 114 рядків коду):
  заощаджене на оголошенні полів пішло на довший `fromCsv`.

Що **не змінилося**: публічний API класу, незмінність полів,
константність, `==`/`hashCode`, результати всіх тестів.

### Рівність за значенням

`Expense` перевизначає `==` і `hashCode` разом (через `Object.hash`).
Експеримент: після видалення `hashCode` дві рівні за `==` витрати
отримали різні хеш-коди, і `Set` з них мав розмір 2 замість 1 —
множина шукає елемент за хеш-кодом і до `==` навіть не доходить.
Аналізатор попередив про це правилом `hash_and_equals`.

Щоб рівність витрат працювала, рівність за значенням визначено й для
способів оплати (у `Cash` і в домішці `MaskedNumber`).

### Запечатана ієрархія і `switch` без `default`

Функція `paymentKind` визначає вид оплати `switch`-виразом без гілки
`default`. Оскільки `PaymentMethod` запечатаний, компілятор сам
перевіряє, що враховано всі підтипи. Експеримент: після додавання
четвертого підтипу `CryptoPayment` аналізатор видав помилку
`non_exhaustive_switch_expression` саме у `paymentKind`. З гілкою
`default` новий підтип мовчки потрапив би в «інше».

Гілки для карток використовують зіставлення зі зразком з охоронцем:
`CardPayment(:final number) when number.startsWith('4') => 'Visa'`.
Ще одне зіставлення з охоронцем — у `PaymentMethod.tryParse`, де
зразок списку перевіряє і кількість частин, і формат номера.

### Домішка `MaskedNumber`

Маскування номера (`картка •••• 9876`) потрібне картці й переказу, але
не готівці. Успадкування тут не підходить: довелося б вводити проміжний
клас «спосіб оплати з номером», а в запечатаній ієрархії це означало б
ще один підтип, який треба враховувати в кожному `switch`. Домішка додає
поведінку двом класам, не змінюючи ієрархію.

Домішка має обмеження `on Describable`. Воно звужує коло класів, до яких
її можна підмішати, і відкриває всередині доступ до `label`.

Спершу обмеженням був сам `PaymentMethod`, і це виявилося помилкою:
домішка `on PaymentMethod` стає підтипом запечатаного класу, і `switch`
у `paymentKind` перестав бути вичерпним — аналізатор вимагав гілку
`MaskedNumber()`. Тому обмеження перенесено на окремий інтерфейс
`Describable`, який реалізує `PaymentMethod`.

### Узагальнене сховище

`Repository<T extends Identifiable>` зберігає елементи в `Map` за `id`.
Обмеження параметра типу дає дві речі: усередині класу компілятор знає,
що кожен елемент має `id` (без обмеження вираз `item.id` не
скомпілювався б), а створити `Repository<int>` неможливо.

### Методи розширення

- `extension ExpenseDate on DateTime`: `toDisplayDate()`
  (`ДД.ММ.РРРР`), `dateOnly`, `daysUntil(other)`. Замінили функцію
  `formatDate` з ЛР 1: виклик `date.toDisplayDate()` читається
  природніше.
- `extension SumOf<T> on Iterable<T>`: `sumOf(selector)` — сума числової
  ознаки елементів; прибирає повторюваний `map(...).fold(0.0, ...)`.

### Записи й деструктуризація

`amountStats` повертає запис `(min, max, average)`; у звіті він
розкладається зразком `if (... case (:final min, :final max, :final
average))`, який водночас перевіряє результат на `null`. У
`Expense.fromCsv` так само розкладається запис із семи текстових полів.

### Розбір і єдине місце з `try/catch`

У ЛР 1 розбір не використовував винятків. Тепер розбір виконує
конструктор, а конструктор може повідомити про помилку лише винятком.
Функція `parseExpense` — єдине місце, де `FormatException`
перехоплюється й перетворюється на запис `(expense, error)`; решта
програми з винятками не працює.

### Що залишилося з ЛР 1

Конвеєри `where → map → fold`, `fold` замість `reduce` для порожніх
колекцій, замикання `olderThan`, параметр `{DateTime? today}` замість
`DateTime.now()` у значенні за замовчуванням, `StringBuffer` у звіті,
маскування номерів карток у примітках через `replaceAllMapped`.

## Лабораторна робота 3: асинхронність, потоки, ізоляти

### Асинхронне сховище

`AsyncRepository<T extends Identifiable>` імітує повільне джерело
даних: кожна операція (`load`, `require`, `loadAll`, `save`, `delete`)
спершу чекає `latency` і тому повертає `Future`. Дані всередині зберігає
синхронний `Repository<T>` з ЛР 2 — новий клас лише додає очікування,
тож логіку сховища не продубльовано.

Відсутній запис `load` повертає як `null`, а `require` і `delete`
завершуються помилкою `EntityNotFoundException`: так з'являється
операція, яка може «впасти» в групі одночасних запитів.

### Лінти `unawaited_futures` і `discarded_futures`

Обидва правила підсвічують `Future`, якого ніхто не дочекався: перше —
в `async`-функціях, друге — у звичайних. У власному коді вони знайшли
лише навмисні місця в демонстраціях (забутий `await`, `try/catch` без
`await`), які позначено коментарем `// ignore:` з поясненням.

### Забутий `await`

`delete` без `await` лише запускає операцію: на наступному рядку запис
ще у сховищі (16 записів), а видаляється він через 300 мс (15).
Програма не чекає завершення і не дізнається про помилку, якщо вона
станеться.

### Послідовно чи одночасно

Три операції по 500 мс: через три `await` поспіль — **1544 мс**, через
`Future.wait` — **513 мс**. Кожна операція так само чекала 500 мс, але
у другому випадку всі три чекали водночас. Асинхронність не прискорює
обчислення, вона усуває простій під час очікування.

### Помилки в групі операцій

Другий із трьох запитів звертається до неіснуючого запису.

- `Future.wait` кидає першу помилку, і це вся доступна інформація:
  результати двох успішних операцій втрачено, номер невдалої
  невідомий.
- Розширення `.wait` на списку кидає `ParallelWaitError`, у якому є
  `values` (результати, `null` на місці невдалої) і `errors` (помилки,
  `null` на місці успішних): видно стан кожної операції.

### `try/catch` навколо виклику без `await`

Блок `try` завершується, щойно операцію запущено, а помилка з'являється
через 500 мс — коли програма вже вийшла з `try`. Тому `catch` її не
бачить, і вона стає неспійманою (у демонстрації її перехоплює
`runZonedGuarded`, інакше програма аварійно завершилася б). З `await`
функція призупиняється всередині `try`, і помилку ловить звичайний
`catch`.

### Генератор `async*` і його лінивість

`watchAll` видає витрати по одній з інтервалом. Доказ лінивості:
потік створено, 500 мс на нього ніхто не підписаний, і повідомлення з
початку тіла генератора з'являється лише після підписки через
`await for`. Генератор закривається сам, коли перебір закінчено.

### `StreamController` і події змін

`save` і `delete` додають події `ItemSaved` / `ItemDeleted`
(запечатана ієрархія `RepositoryEvent`) у контролер одноразової
підписки. Три події, додані до появи слухача, не губляться: такий
контролер тримає їх у буфері до першої підписки.

Звідси ризик витоку пам'яті: якщо потік ніхто не слухає, а контролер не
закрито, буфер живе стільки, скільки сховище. Тому є метод `close()`.
Генератор `async*` такої проблеми не має — він не працює без підписки і
закривається сам.

### Підписки та їх скасування

Кожна підписка `listen()` зберігається у змінній типу
`StreamSubscription` і явно скасовується через `cancel()`. Подія після
скасування нікуди не надходить.

### Помилка посеред потоку

Потік «витрата — помилка — витрата»:

- `await for` отримує першу витрату, на помилці цикл обривається, друга
  витрата втрачається;
- `listen` з `cancelOnError: false` отримує все: дані, помилку, дані й
  подію завершення.

### Одноразова й широкомовна підписка

Друга підписка на `changes` дає `Bad state: Stream has already been
listened to.` Потік, перетворений через `asBroadcastStream()`, віддає ті
самі елементи двом слухачам одночасно. Широкомовний потік не накопичує
події: те, що надійшло до підписки, слухач не отримає.

### Конвеєр трансформації

`watchAll().where(...).map(...).take(3)` відбирає оплати карткою,
перетворює їх на рядки й зупиняється на трьох. `take` не лише відкидає
решту, а й скасовує підписку на джерело — генератор зупиняється
(видно з повідомлення в його `finally`).

### Ізоляти

`simulateExpenses` генерує 20 мільйонів випадкових витрат і рахує суми
за категоріями — важке синхронне обчислення без `await`. Паралельно
працює таймер на 100 мс: якщо він не спрацював, цикл подій стояв.

| Варіант | Час | Таймер |
|---|---|---|
| Одна симуляція в головному ізоляті | 350 мс | 0 разів |
| Одна симуляція в `Isolate.run` | 350 мс | 3 рази |
| Дві послідовно в головному ізоляті | 660 мс | 0 разів |
| Дві одночасно у двох ізолятах | 346 мс | 3 рази |

Одна операція в ізоляті не стала швидшою, але головний ізолят не
блокувався. Дві операції у двох ізолятах ішли майже вдвічі швидше, бо
виконувались паралельно на двох ядрах — `async/await` цього дати не
може, бо лише перемикається між задачами в одному потоці.

Зміна глобальної змінної всередині `Isolate.run` не видна в головному
ізоляті (там лишився 0): ізолят має власну пам'ять і власні копії
глобальних змінних. Передаються лише значення — аргументи функції й
результат, які копіюються між ізолятами.

### Тести

`expectLater`, `completion`, `throwsA`, `emitsInOrder`, `emitsDone`:
операції сховища, помилка невідомого ідентифікатора, порядок елементів
`watchAll`, порядок подій `changes`, одноразова й широкомовна підписка,
`take`, результат `Isolate.run`. У тестах затримка сховища 5–10 мс,
щоб вони не чекали даремно.

### Файли і шляхи

Журнал зберігається в `data/expenses.json` — масив об'єктів
`Expense.toJson`. Шляхи будуються через `p.join` з пакета `path`, тож на
Windows вийде `data\expenses.json`, а на Linux — `data/expenses.json`.
Відсутній файл означає порожній журнал; каталог створюється під час
першого збереження. Каталог `data/` виключено з репозиторію.

### JSON і явні приведення

`jsonDecode` повертає `dynamic`, тому `Expense.fromJson` приводить кожне
поле явно (`as String`, `as num`). Сума читається як `num`, бо JSON не
розрізняє `100` і `100.0`. Невідповідність типу кидає `TypeError`, який
`fromJson` перетворює на `FormatException`: код, що читає файл чи тіло
запиту, обробляє одну помилку «некоректні дані». Спосіб оплати
зберігається текстом `PaymentMethod.toText()` (`картка:5375…`), оберненим
до `PaymentMethod.parse`.

### Великий файл

`readExpenseFile` читає файл через `openRead() → utf8.decoder →
LineSplitter`: у пам'яті водночас лише кілька рядків. Команда `stats`
обробила згенерований файл на 1 000 000 рядків (≈80 МБ): 999 000
коректних, 1000 пошкоджених, 16,3 с під `dart run`. Пам'яті вона тримає
лише на підсумки за категоріями. Команда `generate` так само пише файл
рядок за рядком через `IOSink`.

### Командний рядок

Команди побудовано на `CommandRunner` з пакета `args`: він сам формує
довідку, перевіряє допустимі значення (`--currency` лише UAH, USD, EUR)
і повідомляє про невідомі команди. `runCli` приймає потоки виводу як
параметри, тож тести перевіряють і вивід, і код завершення в тому самому
процесі.

### HTTP-клієнт і три рівні відмов

Команда `rates` робить два запити до НБУ через один `http.Client`, який
закривається у `finally`. `NbuRatesClient` отримує клієнт ззовні — у
тестах його підміняє `MockClient` з `package:http/testing.dart`.

| Рівень | Перевірка | Результат | Код |
|---|---|---|---|
| з'єднання | несправжній хост | «сервер не відповів за 10 с» | 69 |
| код відповіді | неіснуюча сторінка НБУ | «сервер відповів кодом 404» | 69 |
| тіло | головна сторінка НБУ (HTML) | «некоректне тіло відповіді» | 76 |

Другий рівень показує, чому успішний `await` ще не означає успішного
запиту: виняток не виник, а сторінки немає. Тайм-аут 10 с додано тому,
що несправжній хост не дав миттєвої помилки — без нього програма чекала
б невизначено довго.

### HTTP-служба

Обробники винесено в `lib/src/server.dart`; `buildHandler` повертає
звичайну функцію `Request → Response`, тож тести викликають її напряму.

- **Коди відповіді.** 404 — сутності немає; 400 — запит некоректний
  (тіло не JSON, бракує поля, від'ємна сума, невідома валюта у фільтрі);
  409 — запит коректний, але суперечить стану сховища (такий `id` уже
  є). Некоректний фільтр дає 400, а не порожній список, щоб друкарська
  помилка не маскувалася під «нічого не знайдено».
- **Проміжний обробник** `requestLogger` загортає всі маршрути й пише
  метод, шлях, код і час: `GET /items/E99 → 404 (0 мс)`.
- **Кодування.** Кожна відповідь має `content-type: application/json;
  charset=utf-8`. У PowerShell кирилицю в адресі запиту довелося
  кодувати вручну (`%D0%9A…`): консоль передає її `curl.exe` у своєму
  кодуванні, і служба отримувала спотворений параметр.
- **Невідомі маршрути.** `shelf_router 1.1.5` не має параметра
  `notFound`, тому останнім оголошено маршрут-перехоплювач
  `all('/<ignored|.*>')`, який відповідає 404 у тому самому форматі
  JSON.
- **Збереження.** `bin/server.dart` слухає події `changes` сховища з ЛР 3
  і після кожної зміни записує журнал у файл, тож обробники HTTP не
  знають про файлову систему.
- **Приватність.** Відповіді служби будує `publicJson`: спосіб оплати —
  `картка •••• 9876`, номери карток у примітках замасковано.
  `Expense.toJson` зберігає повні реквізити лише у файлі.

## Оператор `!`, `late`, `dynamic`

У коді **немає** жодного вживання оператора `!` (null assertion) і
типу `dynamic`. Символ `!` трапляється лише в `!=`, у логічному
запереченні й у перевірці типу `is!`.

Приведення `as` вжито лише на межі з JSON — у `Expense.fromJson` і
`ExchangeRate.fromJson`, де дані приходять з файлу чи мережі як
`dynamic`. Кожне приведення загорнуто так, що помилка типу стає
`FormatException`.

Ключове слово `late` є лише в тестах: `late AsyncRepository<Expense>
repository;` перед `setUp`. Це стандартний прийом `package:test`: змінна
отримує значення перед кожним тестом, тож кожен тест працює зі свіжим
сховищем. У коді бібліотеки й програм `late` немає.

Замість `!` використано:

- `??` з виразом `throw` — `double.tryParse(text) ?? (throw
  FormatException(...))`;
- зіставлення зі зразком, яке водночас перевіряє на `null` і розкладає
  значення (`if (... case (...))`, `switch`);
- `?.` у тестах.

У `analysis_options.yaml` увімкнено `strict-casts`, `strict-inference` і
`strict-raw-types`, тож неявний `dynamic` теж не пройде аналіз.
